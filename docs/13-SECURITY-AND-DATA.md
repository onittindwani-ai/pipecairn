# Security and data

## What the app does

- Sign in with email and password (the sign in request is limited to 4 KB). Passwords are stored only as argon2 hashes. Sessions are signed, httpOnly cookies. Five wrong tries at one account from one address slow down fast, a wider limit counts every try from one address, and spaces or capitals in the email never give a fresh set of tries. There is deliberately no limit on one account across all addresses, because it would let a stranger lock the owner out of their own system by typing wrong passwords.
- The app refuses to start with an example or short `SESSION_SECRET` when `DEMO_MODE=false` or whenever `OWNER_PASSWORD_HASH` is set, and refuses `DEMO_MODE=true` on Postgres. The public demo password, the made up approver and viewer accounts and the demo data reset (which erases every table) exist only while `DEMO_MODE=true` AND no `OWNER_PASSWORD_HASH` is set.
- Writes from the browser must carry a special header, which blocks cross site tricks. The web app refuses to forward login and webhook calls.
- Webhooks are verified before anything is read: Telnyx by Ed25519 signature with a 5 minute window, Cal.com and the email and form hooks by HMAC. Bodies over 1 MB are refused before they are read in full. The email and form hooks accept an `x-timestamp` header and then sign `timestamp.body`, so a captured request stops working after five minutes; the same message sent twice is stored once.
- Email connections check the server certificate; plain text mail is refused for any host except this same computer.
- A complete request to stop in a reply is honoured at once and suppresses the address for good: "unsubscribe", "remove me from your list", "stop emailing me", "do not contact me", and the one word texts STOP, STOPALL, QUIT, CANCEL, END or "Please stop" when that is the whole message ("cancel my Tuesday meeting" is not a stop). It wins over bounce wording in the same message ("please unsubscribe me, this address is no longer used" is an opt out). The subject counts too, because the unsubscribe link in an email sends the subject "unsubscribe", but `Re:` is dropped and a subject that is one of ours is ignored (a campaign called "Stop writing follow up emails by hand" is not a request to stop).
- Wording that only might be a stop ("can we block this Thursday", "I'll loop in our legal team", "remove the setup fee", "please stop sending the PDFs, just call me", "forward to my attorney", "this unsolicited message is actually relevant") does **not** suppress anyone. The follow ups to that person stop, the reply stays open in the Inbox with a note saying which words made the reader careful, and a person decides: **Never contact this person again** makes it permanent, or they answer by hand. An owner can undo a stop that was read wrongly with **Lift the stop (owner)** on the reply (or `POST /api/leads/{id}/lift-suppression`): it removes that person's address and number from the list, leaves them out of any sequence (a person writes to them), keeps a stop on their whole domain, and is written to the audit log with the reason.
- A bounce is believed only when it is a real delivery status report that names a message this system sent and says, in its own `Action` and `Status` lines, that delivery failed for good (a 5.x.x status), so a forged "mail delivery failed" cannot suppress anyone or pause a mailbox, and a "delayed" or "mailbox full" report changes nothing. A plain reply that only sounds like a bounce ("refused by our spam filter, but I am interested") changes nothing about the address or the mailbox, but it stops the follow ups to that person and stays open for a person, so the next step does not go out to someone who just answered. When the mail server itself refuses an address while sending, only a real bad address counts (an enhanced status of 5.1.x, or 550, 551 or 553 without wording about relaying, blocking or policy). Any other refusal (a blocked sending address, "relay denied", a spam list, a full mailbox, code 554) is the mailbox's problem: the message is tried again later, it never counts against the person, nothing is suppressed, and the Audit page gets a `mailbox.server_refusal` note. The Audit page notes how each stop request was authenticated.
- An automatic reply is recognised by its words ("out of office", "automatic reply") or by an auto reply header (`Auto-Submitted`, `X-Autoreply`). A date or a ticket number alone ("I'm back in the office next Tuesday", "re ticket #4412") is not enough: that reply stops the follow ups and stays open for a person instead of being filed away.
- The kill switch and "force draft" set in the app also stop the CRM sync, not only sending.
- Every email carries a footer (your company, address and how to stop) and `List-Unsubscribe` headers; with `PUBLIC_BASE_URL` set it also has a signed one click unsubscribe link.
- Adapter addresses are checked so a setting cannot point at a private network (server side request forgery guard).
- Anything a lead writes is wrapped as untrusted text before a language model sees it. The model can suggest a reply; it cannot send, change settings or switch live sending on.
- Every important action goes in a hash chained audit log. **Verify the chain** detects edits. The chain is not keyed: someone who can write to the database can rewrite the whole chain and its hashes, so it catches accidents and partial edits, not a determined attacker. Keep backups on another machine. The check reads the newest 20,000 rows by default (`/api/audit/verify?limit=0` reads all of them, in batches).
- The suppression list is re-read from the database before every send, and so are the kill switch and "force draft".
- Each send is recorded as "sending" and committed before the mail server is called, and finished one message at a time. What is guaranteed: this system never sends the same sequence step to the same person twice on its own. If the process dies, or the connection breaks after the message was handed to the mail server, the message is marked unconfirmed and the step counts as done, however late the restart is; a person can look in the Sent folder and, if it is not there, press the button that tries the step again. What is not guaranteed: that a message cut off at that moment was delivered (it may be missing). A message the mail server refuses (the message, or the address for now) is tried at most three times, an hour apart; a problem with the connection, the login or the sender address is retried until it works and never stops a person.
- The mailbox is read without marking mail as read; a message is marked read only after it has been stored, so a failure while storing never marks it read and it is tried again at the next poll. After three failed polls it is kept as "unreadable mail" (sender and subject only) for a person. Mail with an unknown character set or broken encoding is stored as text and flagged; a message that cannot be parsed at all is stored as raw text, the person's follow ups stop, as for any reply, and nothing is drafted or sent from it. Mail is read within limits, because anyone can send it: only the first 256 KB of a message is read (a larger one is read from its first part and marked "large message"), every header value is cut to 2,000 characters, web page tags are stripped in one pass, and a parse that takes more than 5 seconds is stopped and the message kept as raw text. The 5 second stop works in the worker, which runs jobs on its main thread; anywhere else the size limits and the single pass reader are the protection. A stop request is found in readable text only: a stop inside text that could not be decoded may not be recognised, which is why such a message is shown to a person. Mail from an address that is not a lead is left alone (not read, not copied, not marked as read) unless `KEEP_UNMATCHED_MAIL=true`; use a mailbox that is only for this system.
- The public `/health` page says only that the app is up. Roles: the owner changes sequences, imports leads and settings; an approver approves, rejects, books and stops people; a viewer reads.

## What you must do

- Keep `.env` out of git. Use long random values for `SESSION_SECRET` and `WEBHOOK_SHARED_SECRET`.
- Put the API and web behind HTTPS.
- Keep keys to the minimum scope (HubSpot write only, a Telnyx key for messaging only).
- Back up, and rotate any key you suspect leaked. If you replace `SESSION_SECRET`, everyone is signed out and the unsubscribe links in emails already sent stop working; put the old value in `SESSION_SECRET_PREVIOUS` so those links keep working.

## Personal data

Leads are personal data. You decide the retention period. To remove a person, add them to the suppression list first (so they are never re-imported and contacted), then delete the lead if the law or they ask. Keep a suppression record even after deletion, otherwise a re-import could contact them again.
